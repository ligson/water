# 本地模型优化设计

Water 第一阶段面向本地或内网模型。相比线上强模型，本地模型通常上下文更短、工具调用稳定性更弱、复杂任务规划能力也更不稳定。因此 Water 不能依赖模型一次性理解整个仓库，而要通过 Harness、索引、缓存和上下文压缩来提升可用性。

## 1. 设计原则

- 不区分模型能力档位。第一版不做“写代码模型 / 总结模型 / 工具模型”的能力画像。
- Provider 只负责连接和默认参数，不负责复杂路由。
- Harness 负责把大任务拆小，把上下文喂准，把中间噪声压缩。
- 模型看到的是 Context Pack，不是完整项目。

## 2. Codex 可借鉴的公开思路

公开 Codex 文档能确认以下方向：

- Codex CLI 有 `/compact`，用于把可见聊天总结成更短上下文，以保留关键点并释放 token。
- Codex App Server 有 `thread/compact/start`，可以手动触发线程历史压缩，并通过任务事件流返回进度。
- Codex 文档建议避免把探索笔记、测试日志、堆栈、命令输出等噪声塞满主上下文；更好的方式是保留需求、约束、决策和总结。
- Codex 技能系统使用 progressive disclosure：先只给模型技能名称和描述，真正选中技能时再读取完整说明。

公开资料没有说明 Codex 内部如何做文件摘要缓存、召回排序或压缩算法。Water 不假设这些内部实现，只借鉴“压缩历史、减少噪声、按需加载”的方向。

参考：

- Codex Manual: `/compact`
- Codex Manual: `thread/compact/start`
- Codex Manual: progressive disclosure for skills

## 3. Water 的 Context Pack

每次 Turn 调用模型前，由 `internal/agent` 和 `internal/harness` 生成 Context Pack。

建议结构：

```text
System Rules
Project Rules
Workspace Summary
Task Goal
Current Plan
Pinned Context
Relevant File Summaries
Relevant Code Snippets
Recent Tool Results Summary
Open Approvals / Constraints
```

原则：

- 优先放目标、约束、决策。
- 文件只放摘要和必要片段，不整仓塞入。
- 命令输出默认摘要化，避免长日志污染上下文。
- 工具结果需要结构化，方便压缩和回放。

### Token 预算

Context Pack 最多使用 Provider 配置上下文窗口的 80%。

剩余 20% 作为输出、工具结果回填、模型格式波动和本地模型 tokenizer 估算误差的安全余量。

第一版不需要做过细的动态分配，但建议使用以下基础比例：

- 系统规则、项目规则、工作区规则：10%。
- 任务目标、当前计划、任务滚动摘要：20%。
- 钉住上下文：25%。
- 相关文件摘要与代码片段：30%。
- 最近工具结果摘要、审批约束、错误摘要：15%。

当某一类内容不足时，空出的预算可以让给相关代码片段和钉住上下文。

## 4. 缓存策略

Water 第一版应当做缓存。

### 文件摘要缓存

缓存字段建议：

- `workspace_id`
- `path`
- `content_hash`
- `language`
- `summary`
- `symbols`
- `imports`
- `updated_at`

文件内容 hash 不变时复用摘要；文件变更后重新生成摘要。

### 工作区索引缓存

先做轻量索引，不引入复杂向量库：

- 文件树。
- 文件大小、语言、修改时间。
- README / AGENTS / docs 摘要。
- SQLite FTS5 全文索引。
- 符号索引：函数、类型、接口、组件名。

### 任务滚动摘要

每个 Task 保存滚动摘要：

- 用户目标。
- 已确认约束。
- 已读取文件。
- 已修改文件。
- 已做决策。
- 最近错误和验证结果。
- 下一步建议。

当上下文接近模型限制，或者用户手动触发压缩时，用滚动摘要替代老消息和噪声输出。

### 压缩模板

文件摘要、任务摘要、工具输出摘要的 prompt 模板由系统预置，第一版不暴露给用户配置。

系统预置模板需要稳定输出结构化结果，重点保留：

- 用户目标和约束。
- 关键决策。
- 文件职责与主要符号。
- 已修改内容。
- 错误、验证结果和下一步。

后续如果需要高级自定义，可以再在 Provider 或工作区设置中增加模板覆盖能力。

## 5. 压缩触发

第一版建议支持三种触发：

- 自动触发：估算 Context Pack 超过 Provider 上下文预算的一定比例。
- 手动触发：前端任务页提供“压缩上下文”入口。
- 阶段触发：工具执行、测试运行、长日志结束后生成摘要。

压缩不是删除历史。完整事件和消息仍保存在 SQLite；压缩只影响下一次喂给模型的上下文。

## 6. 用户钉住上下文

用户可以把文件、目录或说明钉住到当前任务或工作区。

建议第一版先支持：

- 任务级钉住文件。
- 任务级文本备注。
- 工作区级默认说明。

被钉住的内容优先进入 Context Pack，但仍要受 token 预算控制。

### 钉住上下文超预算裁剪

钉住上下文参考 Codex 公开文档中的按需加载、压缩和减少主上下文噪声思路处理。公开文档能确认 Codex 支持 `/compact`、`thread/compact/start`，以及技能系统的 progressive disclosure；但没有公开具体的钉住文件裁剪算法。

Water 第一版采用以下规则：

1. 当前用户消息里明确提到的文件或目录优先级最高。
2. 任务级钉住内容优先于工作区级默认说明。
3. 文件优先放摘要和关键片段，只有预算足够时才放完整内容。
4. 目录钉住默认放目录摘要、文件列表和相关文件摘要，不展开整个目录。
5. 超预算时保留路径、摘要、关键符号和最近修改片段，丢弃长正文。
6. 如果用户明确要求“完整阅读”某个文件，而预算不足，Harness 应分段读取并让模型逐步处理，不一次塞满上下文。

## 7. 工具意图兼容

本地模型不一定稳定支持 OpenAI 原生 `tool_calls`。

Water 第一版建议支持两种来源：

- OpenAI-compatible 原生 `tool_calls`。
- 模型输出约定 JSON。

Harness 内部统一转换成：

```text
ToolCall {
  id
  name
  arguments
  source
}
```

解析失败时不要直接执行任何动作，应要求模型修复结构化输出，或降级为普通文本并提示用户。

## 8. MVP 取舍

MVP 要做：

- 文件摘要缓存。
- 工作区轻量索引。
- 任务滚动摘要。
- Context Pack 组装。
- 手动压缩入口。
- 长工具输出摘要。

MVP 暂不做：

- 向量数据库。
- 多模型路由。
- 模型能力评分。
- 自动选择“编码模型 / 总结模型”。
- 复杂上下文可视化。
